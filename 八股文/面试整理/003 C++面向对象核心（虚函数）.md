```
class Base { 
public: 
	Base() { cout << "Base Con" << endl; } 
	~Base() { cout << "Base Des" << endl; } // 注意：这里没有 virtual 
};
class Derived : public Base { 
public: 
	Derived() { cout << "Derived Con" << endl; } 
	~Derived() { cout << "Derived Des" << endl; } 
};

int main() { 
	Base* p = new Derived(); 
	delete p; 
}
```
**问题 1：** 请说出控制台打印的完整输出顺序。
	Base Con， Derived Con，Base Des
	这是因为这里的~Base()不是虚函数，当编译器处理delete p的时候，p的类型只是Base*，于是多态失效，只清理了基类部分，
**问题 2：** 这段代码有什么严重的 Bug？为什么？
	内存泄漏 (Memory Leak) / 未定义行为 (Undefined Behavior)。
	如果 `Derived` 类中申请了资源（比如 `int* ptr = new int[100];`），由于 ~Derived() 永远不会被调用，这块内存就永远无法释放。在服务器或游戏引擎这种长时间运行的程序中，这会导致内存耗尽，程序崩溃。
**问题 3：** 为什么 C++ 默认的析构函数不是虚函数？”
	为了**性能**和**内存紧凑性**（“不为不用的东西买单”）。
1. **空间开销：** 如果析构函数默认为 `virtual`，那么**每一个**类（即使是简单的 `struct Point {int x, y;}`）都会被强行插入一个 **vptr (虚表指针)**。
    - 这会导致对象大小增加（32位加4字节，64位加8字节）。对于像 `Point` 这样的小对象，体积直接翻倍，这是不可接受的。
2. **时间开销：** 虚函数调用需要查表（vtable），比普通函数调用慢。
3. **结论：** 只有当类被设计用来**当做基类**使用时，程序员才应该手动声明 `virtual`。
**"构造函数：先父后子。** **析构函数：先子后父。** **如果父类析构不加 Virtual，子类析构根本不跑。"**


## 虚函数知识点总结

```
class A {
public:
    int x;               // 4字节
    virtual void func(); // 虚函数 1
    virtual void g();    // 虚函数 2
};
<!--ID: 1773027655279-->


class B : public A {
public:
    int y;               // 4字节
    void func() override; // B 重写了 func
    // B 没有重写 g，直接继承
};

A* p = new B(); // 父类指针指向子类对象
```
### . 宏观视角：三块内存区域
要理解布局，首先要明白这三个东西分别存在哪里，它们是完全分开的：
1. **对象实例 (Object Instance)** —— 在 **堆 (Heap)** 上。
    - 这是 `new B()` 申请出来的内存。
    - 它里面存的是：**数据** 和 **一个神秘的指针 (vptr)**。
2. **虚函数表 (vtable)** —— 在 **只读数据段 (.rodata)** 上。
    - 这是**编译器**在编译时候就生成好的。
    - **每一个类**（注意是类，不是对象）只有一张表。所有 `B` 类的对象共用这一张表。
3. **函数代码 (Code Segment)** —— 在 **代码段 (.text)** 上。
    - 这是 `A::func`, `B::func` 这些函数的二进制指令

### 2. 微观视角：内存里的“寻宝图”
现在，我们把镜头拉近，看看 `p` 指针到底指向了什么。
<!--ID: 1773027655283-->

#### 第一块：对象内存布局 (Class B Object)
当你执行 `new B()` 时，内存里申请了这样一块连续的空间（假设 64 位系统）
<!--ID: 1773027655285-->


| **内存偏移 (Offset)** | **内容**          | **说明**                                        |
| ----------------- | --------------- | --------------------------------------------- |
| **0x00**          | **vptr (虚表指针)** | **这是编译器偷偷插入的！** 占据前 8 字节。它指向 **B 类的 vtable**。 |
| **0x08**          | **A::x**        | 继承自父类 A 的成员变量 `x` (4字节 + 4字节padding对齐)。       |
| **0x10**          | **B::y**        | 子类 B 自己的成员变量 `y`。                             |
**重点：** 对象内部**绝不存储**函数代码，也不存储整个表，它只存了一个**指针 (vptr)**。
#### 第二块：虚函数表布局 (Class B vtable)
这是一个**函数指针数组**。因为 `B` 重写了 `func`，但没重写 `g`，所以这张表长这样：
<!--ID: 1773027655287-->


| **数组下标 (Index)** | **存放的地址 (Pointer)** | **指向哪里？**                             |
| ---------------- | ------------------- | ------------------------------------- |
| **[0]**          | **&B::func**        | 指向 **B 类** 重写后的 func 代码地址。            |
| **[1]**          | **&A::g**           | 因为 B 没改写 g，所以这里依然指向 **A 类** 的 g 代码地址。 |
| [2]              | NULL/RTTI           | (通常结尾会有结束符或指向 RTTI 类型信息的指针，暂不展开)      |
### 3. 动态调用流程：CPU 是怎么跑的？
当你写下 `p->func()` 时，发生了什么？我们来看一下 CPU 的**“四步走”**操作（伪汇编逻辑）：
1. **取对象头：** CPU 拿到指针 `p`，去读取它指向内存的**前 8 个字节**。
    - 这就是拿到了 **vptr**。
2. **找表：** 根据 `vptr` 的地址，跳到了 **B 类的 vtable**。
3. **查表 (Lookup)：** 编译器知道 `func` 是这类中的**第 1 个**虚函数。
    - 所以 CPU 读取 vtable 数组的**第 0 个元素**。
    - 读出来的值是 `0xAAA...` (即 `B::func` 的代码地址)。
4. **跳转 (Call)：** CPU 执行 `call 0xAAA...`。
    - **Bingo!** 执行到了 `B::func`

### 4. 对比：如果是 A 类的对象会怎样？
如果代码是 `A* p2 = new A();`，内存布局唯一的区别在于 **vptr**：
1. `p2` 对象里的 `vptr` 指向的是 **A 类的 vtable**。
2. **A 类的 vtable** 长这样：
    - `[0]: &A::func` (注意：这里是 A 的 func)
    - `[1]: &A::g`
所以，同样的指令 `p2->func()`，因为 `vptr` 指向的表不同，查表查出来的地址就不同，这就是**多态**。

### 5. 校招常考总结（一定要背下来的点）

1. **vptr 在哪里？**
    - 通常在对象内存的**最前面**（0 偏移处），为了高效存取。
2. **vtable 在哪里？**
    - 属于类，静态存在**只读数据段**（全局共享）。
3. **多态的代价是什么？**
    - **空间：** 每个对象多 8 字节 (vptr)。
    - **时间：** 每次调用多一次内存寻址 (查表)，且**打断了 CPU 流水线和指令预测**（这是引擎优化的重点）。
